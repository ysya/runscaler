# Native Actions Cache v2 Design

Status: architecture approved on 2026-11-11; isolated implementation authorized. Host cutover remains a separate approval gate.
Baseline: Runscaler v0.17.0 (`5cab9dff768d5974e4ae59da416ae9a1a585ad2d`). Rust reference: the deployed cache-server v10.0.0 image's embedded source revision `falcondev-oss/github-actions-cache-server@1b4323045263b70e95a8f1bae81f0ed527f4dc02` (same Git tree as the v10 source tag recorded in Runscaler's compatibility report).

## What to carry over from the deployed Rust server

Use its verified route and client behavior as the compatibility reference: three cache-v2 Twirp methods in JSON and protobuf; `/devstoreaccount1/upload/{id}?sig=...` with Azure Put Blob/Block/Block List responses and `x-ms-request-id`; JWT issuer/JWKS validation and repository/`ac` scope permissions; separate in-progress upload reservations; complete parts hidden until database promotion; reader protection during eviction; 90%-of-budget LRU target; and fixed-origin Results passthrough for artifacts. The Go service is an independent implementation, not a Rust SQLite reader or a wrapper around its container.

Intentional differences require tests: GitHub-style immutable completed keys instead of Rust replacement; parse and honor block-list order and verify `size_bytes` instead of Rust's no-op block-list and count-only finalization; expiring download capabilities instead of Rust's persistent `/download/<UUID>` bearer path; stream proxied request bodies instead of Rust's whole-body buffering. The Go store can use in-memory reader pins because one manager process owns the store; Rust's database leases also serve its multi-worker/storage-adapter design. Retain completed part files as the first-version object and stream them in manifest order; defer Rust's lazy merge until measurements show repeated-read cost warrants it.

Pinned Rust sources: [cache RPC](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/routes/cache.rs), [Azure transfer routes](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/routes/transfer.rs), [storage lifecycle](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/storage.rs), [JWT/JWKS scopes](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/scope.rs), [eviction/cleanup](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/cleanup.rs), and [Results passthrough](https://github.com/falcondev-oss/github-actions-cache-server/blob/1b4323045263b70e95a8f1bae81f0ed527f4dc02/src/routes/passthrough.rs).

## Intent and boundaries

Run a persistent GitHub Actions cache-v2 receiver in the Runscaler Go manager process on one fixed Linux host. Store cache payloads and metadata on that host under a manager-owned directory. Preserve existing cache-v2 steps for the accepted `actions/cache`, setup-go, setup-node/npm, Gradle basic, Rust GitHub-provider, and BuildKit `type=gha,version=2` clients. Keep the verified cache-capable runner image boundary: the stock runner overwrites the custom Results URL. Artifacts remain on GitHub through a fixed Results passthrough. Registry and S3 BuildKit cache declarations, package registries, and mutable BuildKit cache mounts are separate backends and are not redirected.

An opt-in receiver has its own private listener and data directory; the existing health listener remains separate. Its configuration is global, not per scale set. A scale set opts in with its existing `docker.actions-cache-url`, which must equal the receiver's advertised URL when using the native receiver. No cache receiver or data directory is created by default. Linux amd64 is the first acceptance target.

## Proposed configuration and operator surface

Add a global `[actions-cache]` table: `enabled=false`, `listen-address` (a concrete private host IP and port, required when enabled), `advertise-url` (absolute HTTP(S) URL with trailing slash, required), `data-dir` (absolute, manager-owned path, required), `max-size-bytes` (positive, required), `max-idle-days=30`, `token-issuer` (default `https://token.actions.githubusercontent.com`), `jwks-url` (optional pinned operator override for controlled tests/GHES), `audiences` (optional exact accepted values, matching the deployed Rust default; enforce if configured after validating real-token claims), and `upstream-results-url` (default `https://results-receiver.actions.githubusercontent.com`, fixed HTTPS origin). Validate no userinfo, query, or fragment in URLs, no wildcard listener, port collision, and local directory ownership/mode before accepting jobs. A test-only configuration may use a private HTTP issuer, never an untrusted JWT-provided URL. Do not offer a production `skip-token-validation` switch.

The systemd service user already has `/var/lib/runner` writable in the generated unit; a native directory there avoids changing the unit for the default deployment. A custom path needs a reviewed writable-path provision. Expose cheap receiver readiness and byte/entry counts in health/status and `runner cache`, without routing this data through the generic wipeable cache-volume cleanup. No management HTTP API is needed for the first release. Logs and metrics must omit bearer tokens, capability URLs, payloads, and full request paths containing signatures.

## Wire protocol and routing

Implement `POST /twirp/github.actions.results.api.v1.CacheService/{CreateCacheEntry,FinalizeCacheEntryUpload,GetCacheEntryDownloadURL}` for `application/json` and `application/protobuf`. Use verified generated protobuf message types and `protojson` so int64 JSON fields, snake-case wire names, optional metadata, and unknown fields behave consistently. Use the Twirp status/error shape for invalid input, unauthenticated, permission denied, conflicts, and internal errors. Bound RPC body size. Do not add a general Twirp framework dependency for three methods.

Return only local signed upload/download URLs. Keep the Rust-compatible `/devstoreaccount1/upload/{id}?sig=...` shape. Support Azure-style `PUT` single-shot blobs, `PUT ?comp=block&blockid=...`, `PUT ?comp=blocklist` with ordered XML block IDs, and `GET`/`HEAD` plus byte-range downloads on opaque local payload paths. Return the `201` and `x-ms-request-id` expected by the existing clients. Stream bodies to disk and downloads from disk; bound request sizes and concurrency. Accept the headers/status codes the pinned Azure SDK and BuildKit clients actually use; pin them with fixture and real-client tests.

Route every CacheService method, local payload path, and legacy `/_apis/artifactcache/` path locally, including unknown methods. Unknown cache operations fail closed; they must never reach GitHub. Forward other Results requests to the configured fixed upstream with `httputil.ReverseProxy`, preserving the request method, body, relevant headers, and upstream response. The upstream must not be chosen from client input. Artifact upload/download may legitimately use GitHub-returned storage URLs; cache payload URLs may not.

The current accepted fork sets `ACTIONS_RESULTS_URL` to the custom endpoint but still supplies GitHub's `ACTIONS_CACHE_URL` to legacy v1 clients. To guarantee local-only cache payloads for unsupported v1 actions, the rollout also needs a separately reviewed, newly pinned fork image that points `ACTIONS_CACHE_URL` at the local receiver (which returns an explicit v1 rejection), or an independently proven equivalent fail-closed mechanism. Until that gate passes, promise local-only payloads only for the measured v2 clients; never describe the existing image as a universal no-cloud-cache guarantee. Do not modify the deployed image during Go implementation.

## Authentication and authorization

Trust only operator-configured issuer/discovery/JWKS locations. Fetch keys with HTTPS, bounded timeouts/response sizes, cache them, and refresh on a bounded schedule or unknown `kid`; never follow token-controlled `jku`/`x5u` or arbitrary redirects. Verify allowed asymmetric algorithm, signature, exact issuer, configured audience, `nbf`, and `exp` before interpreting claims. Reject unknown keys when refresh fails, invalid `ac`, or missing repository identity. Never log raw tokens or claims containing secrets.

Derive repository ID and branch access from the verified JWT's `repository_id` and `ac` scope/permission list (read bit 1, write bit 2). Canonicalize a signed numeric/string repository ID to a nonempty database string; the existing controlled fixture uses opaque string IDs, while protobuf metadata uses int64. Treat RPC `metadata` as untrusted: reject any supplied repository/scope that contradicts the token, and never grant access from it. Save requires the first writable grant, as Rust does; finalize requires the same repository, scope, key, and version reservation and write permission. Lookup searches readable grants by descending permission, retaining token order among equal grants; within each scope it tries primary exact, primary prefix, then each restore key exact and prefix, newest completion first. A read-only token may restore but may not reserve/finalize. Repositories and branches are isolated by the metadata identity, not by key names.

Payload URLs are HMAC-signed, operation-bound bearer capabilities with an opaque ID and expiry; the signing key is generated once and stored mode 0600 beside the database, included in coordinated backups. Upload capabilities bind to a reservation and stop working after finalize/expiry; download capabilities bind to one immutable object ID so a later lookup or eviction cannot silently return different bytes. Use constant-time MAC comparison, strict path parsing, bounded expiry, and no URL logging. Suggested initial lifetimes are 2 hours for upload and 1 hour for download; verify against the pinned clients' delayed fetch/retry behavior during acceptance.

## Durable store and concurrency

Use a new SQLite database in WAL mode (a single explicitly justified Go SQLite driver dependency) with a schema version, plus `staging/` and `objects/` on the same filesystem. Do not reuse the Rust SQLite schema or mount its volume into Go. The schema records `(repository_id, scope, key, version)` identity, reservation state/expiry, object ID, size, timestamps, and block manifest. Use a unique constraint to serialize competing reservations and completed entries.

Choose GitHub-style immutable completed keys: the first completed `(repository, scope, key, version)` wins; later reservations return conflict, and a concurrent in-progress reservation also conflicts. This deliberately differs from Rust v10 replacement. BuildKit v0.34.2 uses numbered `index-...#N` keys for mutable indexes, so its exporter should still work; its actual import/export is an acceptance gate, not an assumed proof. Download capabilities for completed objects never point to a replacement.

Each block upload writes to a private temporary file and renames only after a complete body and fsync. A cancelled/truncated request deletes its temporary file; other staged blocks remain invisible. Block-list commit records the ordered, fully staged block IDs; unlike Rust's index extraction, this treats opaque Azure IDs as opaque. Finalize checks that every listed block exists and that their combined length equals declared `size_bytes`, then commits the immutable part manifest and cache entry in one SQLite transaction. No full-payload copy is needed at finalize. A crash before commit leaves hidden parts for later cleanup; a committed entry never points to a partial block. On restart, unfinalized reservations remain hidden and expire after an idle grace period. Downloads stream the manifest's parts (including ranges spanning parts) while an in-memory reader pin prevents eviction; a later measured optimization may merge parts lazily.

Enforce the absolute completed-payload budget and 30-day idle retention with one receiver-owned sweeper. Evict least recently used completed entries until below 90% of budget, matching Rust's target; protect in-progress downloads and do not delete unrelated files. If post-finalize eviction fails, retain the successfully published entry, report degraded storage status, and retry cleanup, as Rust does. Before issuing a download URL, verify the referenced parts exist; purge a dangling metadata entry and retry matching rather than give BuildKit a URL that will fail after a reported cache hit. Staging and concurrent uploads need separate free-space headroom; the budget is not a hard filesystem quota. Return explicit local errors on ENOSPC, leaving no published partial entry. Backup or restore the whole native directory only while the manager is stopped (SQLite, WAL, objects, signing key); keep it outside the repository.

## Manager lifetime and failure behavior

Start and bind the receiver before scale-set listeners accept jobs. If native cache is enabled but its directory, key, database, JWKS bootstrap, or listener is unavailable, fail startup rather than dispatch cache-enabled jobs. Keep cache and artifact passthrough serving throughout the manager's SIGTERM/SIGQUIT drain while existing runners finish. After all controllers finish, stop accepting new cache requests, wait a bounded period for in-flight transfers, then close the database. A forced second signal or systemd deadline may interrupt transfers; partial uploads stay hidden and recover as misses after restart. Avoid the current health server's 10-second read/write timeouts on the streaming receiver. `readyz` must report receiver failure without implying a cloud fallback.

Because the receiver is in the manager process, every manager restart creates a brief receiver outage. A maintenance window and completed runner drain are required for an endpoint switch; a separate Go process would be a different architecture. Artifacts through Results passthrough are affected by this outage too. If the fixed GitHub upstream is unavailable, artifact requests fail visibly (for example 502); cache RPC/payload handling remains local and never forwards to the upstream.

## Reversible migration

Keep the running Rust v10 service, its external volume, backups, and five-runner scale set untouched while implementing and testing. Start native Go in a separate private port and a fresh manager-owned data directory on an isolated canary environment. New native keys begin cold; no automatic Rust read-through, schema conversion, shared writes, or in-place clearing. Measure cold/warm behavior before considering production opt-in. At an explicitly approved host cutover, drain affected jobs, switch only the selected scale set's `actions-cache-url` to the native advertised URL, and restart the manager with the existing service stop deadline reviewed. Keep Rust running and its data intact for rollback. Rollback drains jobs and restores the Rust endpoint; never clear the endpoint and resume unchanged cache steps, which would send v2 payloads to GitHub. Retire Rust/volume only after a separate backup/retention decision.

## Approval decisions

1. Approve immutable completed keys instead of Rust's completed-key replacement.
2. Approve a fresh native store with cold warming and preserved Rust rollback data instead of an in-place import.
3. Approve the manager-process lifetime and its maintenance-window restart outage.
4. Approve the required fail-closed legacy-v1 runner-image gate before claiming universal local-only cache payloads.
5. Approve the intentional validation/capability differences from Rust: ordered block lists, declared-size checks, expiring download URLs, and optional exact audience enforcement after real-token verification.
