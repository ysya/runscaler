構成ガイド

GitHub Actions ランナーを、Kubernetes なしで。

Runscaler は、Go で実装されたセルフホスト型 GitHub Actions ランナーのオートスケーラーです。各ホストで動く 1 つの管理プロセスが、ジョブごとに一時的な Docker コンテナまたは Tart VM を起動し、完了後に削除します。CLI の実行ファイル名は runner です。

自分の Docker ホストや Apple Silicon Mac を使い、設定ファイルと CLI でランナーの実行容量を管理したい場合に適しています。ホストの用意、ランナーイメージ、認証情報、更新は利用者が管理します。

自分のホストで Docker ランナーを自動スケーリング

Linux の Docker ホストを持ち、信頼できる CI ジョブごとに新しいランナーコンテナを使いたい場合は Docker を選びます。Runscaler は GitHub のランナースケールセット API をロングポーリングし、ジョブが届くとコンテナを起動します。ランナー数はゼロまで縮小でき、Kubernetes クラスターや外部から接続できる Webhook エンドポイントは不要です。

Docker API 1.49 以降（Docker Engine 28.1 以降）、互換性のあるランナーイメージ、GitHub App または PAT の認証情報、十分なホストリソースが必要です。Runscaler は設定されたホスト容量の範囲内でランナー数を調整します。ホストの追加作成は行いません。

  1. Docker の設定を作成し、GitHub URL とスケールセット名を指定します。
  2. Linux のクイックスタートに従って runner をインストールし、設定を保存します。認証情報はホスト上で追加してからサービスをインストールします。
  3. ワークフローの runs-on にスケールセット名を指定します。名前を my-runners にした場合の例：
jobs:
  build:
    runs-on: my-runners
    steps:
      - run: echo "Running on a disposable runner"

セキュリティと分離を確認してください。既定の Docker モードではホストのソケットを共有するため、ジョブはそのデーモンに対して root 相当の制御権を持ちます。任意のジョブ単位 DinD は Docker の状態を分離しますが、特権サイドカーを使用し、ホストのカーネルを共有します。信頼できるコードを実行し、公開フォークからのプルリクエストにこれらの Docker ランナーを開放しないでください。

Apple Silicon でジョブごとに新しい macOS ランナーを実行

Xcode など、ジョブごとに新しい VM が必要な macOS ワークフローには Tart を使用します。Runscaler は用意したイメージを複製し、VM を起動して GitHub ランナーを登録します。ジョブ完了後には VM を削除します。任意のウォームプールで VM を事前に用意することもできます。

ホストには Tart をインストールした Apple Silicon Mac が必要です。互換性のある macOS/Xcode イメージを選び、ログイン中のユーザーの LaunchAgent として管理プロセスを実行します。macOS ゲストはホスト全体で同時に 2 台まで起動できます。イメージ、複製、待機 VM に必要な CPU、メモリ、ディスク容量を確保してください。

Tart は、同じ Apple Silicon ホスト上で、事前に準備した arm64 Linux ゲストイメージにも対応しています。Linux ゲストは macOS VM の起動枠を消費しませんが、実行容量はホストのリソースに依存します。Linux ホスト上で Tart バックエンドを実行できるという意味ではありません。

まず Tart の前提条件を確認し、設定ツールで Tart を選択して、macOS のクイックスタートに従ってください。イメージと GitHub ランナーのバージョンを固定し、保守してください。

Runscaler、ARC、それとも手動管理？

運用したいインフラに合わせて選んでください。以下はデプロイ方式の違いを示すもので、性能の順位ではありません。

デプロイとライフサイクル管理の責任範囲
項目RunscalerActions Runner Controller（ARC）手動管理の GitHub ランナー
実行環境自分の Docker ホスト、または Tart を備えた Apple Silicon MacKubernetes クラスターランナーアプリケーションをインストールしたマシン
ライフサイクルジョブごとにコンテナまたは VM を作成・削除ランナー Pod を管理してスケーリング起動、スケーリング、削除を自分で管理
運用対象各ホストの Go 実行ファイルと TOML、CLI による診断Kubernetes オペレーター、Helm チャート、クラスターリソースランナーアプリケーションと自分のサービスやスクリプト
適した用途既存のホストで Docker や Tart を使用し、Kubernetes を必要としない環境すでに Kubernetes を運用しているチーム固定の実行容量、または独自のライフサイクル管理

GitHub は ARC を Kubernetes オペレーターと説明し、Kubernetes のインフラと運用経験を持つ組織に推奨しています。セルフホストランナーのリファレンスでは、独自のオートスケーラーを作るための独立したスケールセットクライアントも紹介しています。Runscaler は公式の Go スケールセットクライアントを使用する独立したプロジェクトです。

ホスト保守が不要なマネージド CI、クラウドマシンの自動作成、複数ホストにまたがる一元的なスケジューリング、マネージド型の複数ユーザー向け Web コンソールが必要な場合は、別の方式を検討してください。Runscaler は設定された各ホスト上のランナーを管理します。ホスト、イメージ、アクセス方針の運用は利用者が担当します。

よくある質問

Kubernetes や公開 Webhook は必要ですか？

不要です。Runscaler はホスト上で直接動作し、GitHub のスケールセット API への外向き HTTPS ロングポーリング接続でジョブを受け取ります。ホスト、ランナー、VM には、GitHub とジョブが使用するサービスへのネットワーク接続が必要です。

新しいランナーなら、ジョブは完全に分離されますか？

各ランナーコンテナまたは VM は 1 つのジョブを処理しますが、共有ストレージや Docker へのアクセスが分離に影響します。ホストソケットモードではジョブがホストのデーモンを制御できます。ジョブ単位 DinD はデーモンの状態を分離しますが、ホストのカーネルは共有します。Tart は VM の境界を提供しますが、ネットワーク、イメージ、認証情報、明示的な共有リソースには適切な方針が必要です。セキュリティガイドを確認してください。

1 つのプロセスで複数のリポジトリや組織を管理できますか？

はい。同じホスト上に複数のスケールセットを設定でき、ホストが対応していれば Docker と Tart を組み合わせることもできます。管理プロセスのホスト容量を共有しますが、クラスターのスケジューラーではありません。設定ガイドを確認してください。

キャッシュとディスク使用量はどう管理しますか？

Docker スケールセットでは、対応するランナーイメージを使い、ホスト内の Actions キャッシュ受信機能を有効にできます。明示的な共有ボリュームではジョブ間でファイルを保持できます。キャッシュの保持とディスクのクリーンアップは設定が必要です。新しいランナーを使ってもホスト上のすべてのデータが削除されるわけではありません。ホスト内 Actions キャッシュとキャッシュガイドを確認してください。

Runscaler は無料で使えますか？

Sustainable Use License 1.0（SUL） では、個人利用、非商用利用、社内業務での利用は無料です。自社のホストやレンタルサーバーで自社プロジェクトの CI/CD を実行する場合も含まれます。元の著作権表示とライセンス表記を保持してください。v0.23.0 など、MIT ライセンスで公開済みのバージョンには、引き続き同ライセンスが適用されます。

ホストの費用、GitHub の利用条件、Tart とランナーイメージのライセンスは別途適用されます。

Runscaler の販売、ホスティング、有料サービスへの組み込みはできますか？

SUL では非商用目的での無償再配布が認められています。Runscaler 自体を販売したり、有料マネージドサービスとして提供したりする場合は、別途ライセンスが必要です。有料の CI/CD やホスティングのプラットフォームへのプロバイダー統合が SUL の範囲に含まれるか不明な場合は、具体的な利用方法をメンテナーにご相談ください。

アップグレードの互換性は？

バージョン 1.0 より前のため、マイナーリリースでもインターフェースを変更・削除する場合があります。更新前にリリースノートとアップグレード要件を確認してください。
